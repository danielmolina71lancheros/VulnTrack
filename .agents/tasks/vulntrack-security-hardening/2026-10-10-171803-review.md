# Endurecimiento de seguridad del runtime: rate-limit de login, CORS por lista blanca y orquestación con healthchecks

Esta revisión cubre tres frentes del hardening de VulnTrack: una capa Redis con rate-limiting anti fuerza bruta sobre el login, el cierre del CORS abierto por una lista blanca configurable, y la orquestación de `docker-compose` con healthchecks y arranque ordenado, más la alineación del README con la arquitectura real. El rate-limit se respalda en Redis y degrada *fail-open* a propósito: si Redis cae, el login sigue funcionando en vez de bloquearse. El CORS pasa de `cors()` abierto a una whitelist leída de `CORS_ORIGINS` con fallback de desarrollo, y se añade `trust proxy` para que `req.ip` sea fiable. El compose gana healthchecks de Postgres y Redis con `depends_on` en forma larga `service_healthy`, y el README se corrige para dejar de atribuir a Nginx un rol de reverse proxy/TLS que no existe.

Watch for: la degradación *fail-open* del rate-limit (confirmed) es una decisión deliberada que abre una ventana de fuerza bruta mientras Redis esté caído — es correcta para disponibilidad pero conviene tenerla presente. El healthcheck de Postgres usa el superusuario (`DB_USER`), no la cuenta de app, así que no valida que `DB_APP_USER` pueda conectar (likely, de bajo impacto).

**Verdict**: APPROVED

## High-level view

El rate-limiting se apoya en un cliente Redis singleton (`backend/src/config/redis.js`) con conexión perezosa que nunca lanza hacia afuera: cualquier fallo se loguea y devuelve `null`. El middleware `limitarLogin` cuenta intentos por IP y por IP+correo en una ventana de 900s con tope 10, y cuando ambos contadores vienen `null` (Redis inaccesible) deja pasar la petición. Está aplicado exclusivamente a `POST /api/auth/login` en `authRoutes.js`; `/registro` y las rutas MFA quedan intactas.

El CORS ya no acepta cualquier origen: `server.js` construye la lista desde `CORS_ORIGINS` (CSV) con fallback `['http://localhost:5173','http://localhost','http://localhost:80']` y rechaza orígenes fuera de ella, permitiendo peticiones sin `Origin` (curl, healthchecks). `app.set('trust proxy', 1)` precede a las defensas para que la IP del rate-limit sea la real.

La orquestación añade healthcheck de Postgres (`pg_isready`) y de Redis (`redis-cli ping | grep PONG`), y `securehub-api` depende de ambos en forma larga con `condition: service_healthy`, de modo que la API no arranca antes de que sus dependencias estén listas. `CORS_ORIGINS` se inyecta al servicio como `${CORS_ORIGINS}`.

Las cuatro variables nuevas (`DB_APP_USER`, `DB_APP_PASSWORD`, `REDIS_HOST`, `CORS_ORIGINS`) están en `.env` y en `.env.example` en la raíz, sin duplicados. El README refleja ahora la topología real: servicios con nombres `securehub-*`, Postgres 18, el scanner documentado, Nginx descrito solo como servidor estático de evidencias y sin el nodo de reverse proxy/TLS que antes figuraba en el diagrama.

### Fail-open del rate-limit: disponibilidad por encima del bloqueo

`incrementarContador` captura todo error de Redis y devuelve `null`, y `limitarLogin` interpreta "ambos contadores `null`" como "Redis inaccesible" y ejecuta `next()`:

```js
if (conteoIp === null && conteoIpCorreo === null) {
    console.error('[SEGURIDAD] Rate-limit login en fail-open: Redis no disponible');
    return next();
}
```

Mientras Redis esté caído, la protección anti fuerza bruta desaparece por completo; es el riesgo residual aceptado a cambio de no dejar fuera a todos los usuarios ante un fallo de infraestructura. El tope por defecto es 10 intentos en 900s por IP y por IP+correo, así que un atacante no puede diluir el conteo variando solo el correo desde una misma IP. La auditoría del bloqueo (`LOGIN_RATE_LIMITED`) es best-effort dentro de `try/catch`: si falla, el 429 se envía igual.

### Healthcheck de Postgres: valida el servidor, no la cuenta de app

El healthcheck usa `pg_isready -U ${DB_USER}`, el superusuario, no `DB_APP_USER`. Confirma que el servidor acepta conexiones, pero no que la cuenta de bajo privilegio que realmente usa la API pueda conectar ni que las políticas RLS estén activas (likely). El impacto es bajo porque un Postgres sano casi siempre deja conectar a ambas cuentas, pero el check no cubre el fallo específico de "la cuenta de app no existe o no tiene grant".

```
securehub-db   ──pg_isready(DB_USER,DB_NAME)──▶ healthy ┐
                                                         ├─▶ securehub-api (service_healthy)
securehub-redis ──redis-cli -a … ping|PONG──▶ healthy ──┘
```
